# Arlo 阶段推进（Stage Workflow）

一次只处理一个清晰、可验收的 Arlo 路线图阶段、批次或规划任务。路线图描述目标，代码和可重复验证描述事实。

## 1. 选择活动路线图

按以下顺序确定本轮依据：

1. 用户明确指定的路线图、阶段或批次。
2. `AGENTS.md` 声明的当前活动路线图；当前默认是 `docs/roadmap.md`。
3. 活动路线图直接引用的上层计划，只用于定位产品边界和前置依赖。
4. 仍不明确时，仅在 `docs/` 中查找名称或标题含 `roadmap`、`plan`、路线、阶段或里程碑的候选文档，并先检查其定位和状态。

归档、legacy、已完成或被新路线取代的文档不是默认执行清单。`docs/product-redesign-v2.md` 是讨论记录，只有用户明确指定或其中内容已被路线图确认时才作为依据。

只更新本轮选定的活动路线图。不要因为旧路线图仍存在于 `archive/`，就自动修改或勾选它。

## 2. 判断任务模式

### 审阅与规划

适用于审阅、整合、重排、编写或修订路线图，以及用户明确说“不实施”。

- 可以读取代码和执行必要的只读验证来校正计划。
- 只修改用户授权的规划文件，不实施路线图中的代码任务。
- 完成文档与 Git 边界检查后停止，不自动进入第一批实施。

### 批次计划

适用于“规划下一批”“进入下一阶段”“先给计划”或目标批次尚不明确的请求。

- 核对现状并输出一个批次的实施计划。
- 计划至少包括目标、主要文件或模块、实施顺序、关键取舍、风险/降级、验收和建议提交边界。
- 用户确认前不编码。

### 批次实施

适用于用户明确要求实施已有阶段或批次，或已经批准一份具体计划。

- “实施阶段 0”“按已确认计划执行”可视为对该范围的实施授权；先简要报告执行顺序，再推进。
- “审阅阶段 0”“规划阶段 0”不构成编码授权。
- 若批次包含尚未解决且会改变结果的产品选择，先询问必要选择；不要让它阻塞无关的客观修复。

## 3. 建立事实基线

采取任务动作前：

- 完整阅读仓库 `AGENTS.md`、选定路线图相关章节，以及该章节明确要求的直接依据。
- 记录当前分支、`HEAD` 和 `git status`，区分用户已有改动与本轮改动。
- 按“入口 → 调用链 → 配置 → 必要时扩大”的顺序核对代码，不进行无目的的全仓扫描。
- 路线图复选框、报告、分支名和版本描述都不是完成事实；代码、产物和可重复验证优先。
- 发现路线图与代码事实冲突时，先判断是否会改变范围或完成标准；会改变时暂停并报告，不自行扩大批次。

处理已有工作树改动时：

- 无关改动保留并绕开，不清理、不覆盖。
- 与本批目标文件重叠且无法安全区分时，停止并请求用户确认。
- 收尾时用 `git diff --name-only` 和 `git status` 确认最终范围。

## 4. 计划与授权闸门

- 计划必须继承选定阶段已有的目标、非目标、前置依赖、风险和退出条件，不另造平行路线。
- 规划任务使用 [references/plan-template.md](references/plan-template.md)；小修复可以采用精简版，但仍要写清改动文件和验收方式。
- 若发现需要明显改变视觉、功能、内容模型、数据迁移、公开内容或部署方式的事项，先回到计划或请求确认。
- 普通实现细节可以自行判断；用户已明确批准的范围不重复索要确认。
- 不默认提交、推送、部署、创建远端资源或执行破坏性 Git 操作。

## 5. 实施一个批次

- 严格遵守本批范围和非目标，不顺手实施下一批。
- 先处理共同根因，再迁移消费者；避免在多个位置分别打补丁。
- 保持改动小而可审查，每一步尽量可运行、可回退。
- 新发现但不属于本批的问题只记录到路线图的后续候选，不扩大当前任务。
- 遵守仓库 `AGENTS.md` 的文件安全、分层、中文路径、本地化预留和数据兼容约束。
- 阶段 0 的名称/入口清理不得顺手改变快速整理、标签、云端或 UI 方向；这些必须进入各自阶段。

## 6. 验证与路线图状态

验证项目从选定批次的退出条件和 `AGENTS.md` 推导，不用固定命令替代风险判断。

- Python 代码批次通常至少运行 `ruff check src tests`、`ruff format --check src tests` 和 `pytest`。
- 涉及数据库、真实文件、中文路径或入口的批次必须有对应自动化或手动验收。
- 纯文档规划默认检查 Markdown、链接、UTF-8、敏感信息和 Git diff，不运行无关应用构建。
- 失败时区分本轮回归、既有基线和环境限制，只修复本批授权范围内的问题。
- 最终结果区分“通过”“失败”“未执行”“环境无法验证”，不能把未测项写成通过。
- 只有全部退出条件都有代码和验证证据时，才在活动路线图中标记完成；部分完成保持未完成或进行中，并记录剩余项。

需要验证和收尾时使用 `arlo-verify-finish`，不要引用旧的 `scw-*` skill 名称。

## 7. 收尾

最终汇报必须说明：

- 完成或规划了什么；
- 修改的文件和关键取舍；
- 验证结果及未验证项；
- 已知限制、发现但未纳入的问题和下一批建议；
- Git 工作树状态，以及是否提交、推送或部署。

达到当前模式的停止条件后结束：规划任务不开始编码；批次任务不自动进入下一批。

## 硬性规则

- 规划模式或用户明确要求“先讨论/先计划”时，用户确认计划前禁止编码和文件写操作。
- 遵循仓库 `AGENTS.md` 的不可违反规则，尤其是真实文件系统为唯一事实来源、文件操作须用户确认、不得泄露私人内容和不得扩展未经确认的产品范围。
